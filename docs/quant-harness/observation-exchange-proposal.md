# Proposed observation exchange contract

**Proposal, not an implemented API or archive format.** The [JSON Schema](./observation-exchange-proposed.schema.json) and [synthetic examples](./observation-exchange-proposed.examples.json) describe a candidate exchange batch for daily bars, minute bars and adjustment factors. They do not establish a TSP endpoint, provider entitlement, complete history, or permission to move data. `proposed-1` identifies this proposal and is deliberately distinct from the existing Source/archive versions 1 and 2. Changes to these rules require a new proposal version.

## Request and response

A request names a selected source, dataset, explicit symbols, interval/adjustment when applicable, range, limit, opaque cursor and optional prior revision. The proposal does not prescribe a universal page size, rate, automatic schedule or fallback. A trading-date range is inclusive in its named IANA calendar timezone; an instant range is UTC, start-inclusive and end-exclusive. Minute requests use instant ranges. Translating a TSP trade-date request into an instant range needs verified session/calendar boundaries; do not assume every day has the same duration or a complete session.

`complete` means the response finished this request without a continuation or error, not that the underlying market history is complete: coverage can still be `unknown`. `partial` requires a continuation cursor or an explicit error; callers must retain the reason and cannot present it as complete. `failed` has an error and no records. A cursor is opaque and bound to the selected provider and request; do not use it with a changed source, symbol set, window or price basis. Actual source and endpoint are required for non-failed responses, and selected-source requests must not silently fall back. Error messages must be sanitized and cannot carry credentials, headers, tokens or raw provider bodies.

`observedAt` is the receiver's retrieval time, not the provider's publication time. `sourceAsOf` and source timestamps are nullable when unavailable. A trade date is a session identity, not midnight UTC; when an actual source timestamp is supplied for a date-keyed bar, it must map to that date in the stated calendar timezone. Each row retains market, asset type, source time, finality, quality and revision. `unknown` is not zero, final, verified or complete. `verified` quality requires evidence outside this proposal and must never be inferred from HTTP success.

Decimal values are nonnegative base-10 strings, with no exponent; zero is represented as `"0"`, while a missing amount is JSON `null`. Consumers must compare and calculate as exact decimal values or disclose precision loss, and must validate positive prices/factors and OHLC ordering. Units are explicit, including `unknown`; conversion between hands, shares, CNY-thousand and CNY requires verified semantics and must not silently occur. `raw`, `forward`, `backward` and `unknown` are different bases. The `event_ratio`, `cumulative` and `unknown` factor bases are distinct: an unknown factor must not be applied or represented as a TSP event ratio merely because it is numeric.

## Mapping and gaps

| Existing WhyJ boundary | Candidate mapping and missing evidence |
| --- | --- |
| `MarketDataSource` timestamp K-lines and factors | A selected provider and endpoint supply timestamped bars/factors; UTC milliseconds need an exact ISO UTC representation. The facade does not certify original units, coverage, finality, price revisions or source publication time. Factor basis remains unknown. |
| Source `BarObservation` / `FactorObservation` v1 and v1 archive | Kind, symbol, timestamp, source, endpoint, observed time, adjustment and values can be mapped where known. Market, asset type, source-as-of, units, finality, coverage and revision remain unknown; a proposed instant range and paging cannot be reconstructed from a v1 row alone. `factorBasis: unknown` stays unknown. |
| Source `TradingDateBarObservation` v2 and v2 archive | Trade date, Shanghai timezone, nullable actual source timestamp, requested date bounds, Tushare/TickFlow units and adjustment are retained. Its inclusive requested bounds can map to the date range; transport cursor, source-as-of, quality, finality and dataset completeness are not established. A hand is not automatically a share and CNY-thousand is not CNY. |
| `Bar` / `DailyBarDataset` | `Bar` contains a date and numeric OHLCV; `DailyBarDataset` additionally records source, market, retrieval time, unit/adjustment evidence and per-date finality. Mapping requires a verified session date, decimal-to-number precision decision, suitable units, adjustment and finality evidence. It must fail closed when those are insufficient rather than fabricate them. |
| TSP daily/minute/factor views | The pinned TSP schema uses daily `date`, minute `datetime` and factor `trade_date`/`ex_factor`; minute basis can differ across migrated and older data. Those column names alone do not certify equivalent units, timestamps or factor basis. The inspected TSP sync endpoints trigger TSP-side fetching, not a documented ingestion endpoint for this proposal. |

An illustrative daily path is selected provider → `fetchKlines` → `toTradingDateBarObservations` → explicit v2 archive → exact replay; only an eligible consumer with its own calendar, basis and finality evidence may derive a research dataset. An illustrative minute path is TickFlow `fetchKlines` → `toBarObservations` → explicit v1 archive → exact replay; minute consumers must retain unknown units and partial/finality. An illustrative factor path is `fetchAdjustmentFactors` → `toFactorObservations` → explicit v1 archive → exact replay; a consumer must leave the unknown basis unapplied. These are existing local paths, not proof that a TSP consumer receives, accepts or uses those records.

Existing v1 validation can retain zero OHLC values; this proposal requires positive prices as an additional receiver-side semantic check. Such a v1 record cannot be presented as a valid proposed bar without resolving its meaning. The proposal does not rewrite or discard the original archive.

## Validation, corrections and ownership

The schema checks structure, discriminators, decimal syntax, required fields and several status/dataset constraints. It does **not** establish real calendar dates, IANA timezone validity, timezone/date agreement, range membership, source equality, per-request interval/adjustment equality, record uniqueness, OHLC order, positive prices/factors, exact limit enforcement, cursor binding, credential sanitization or provider completeness. A receiver must enforce those conditions before accepting a batch; the focused proposal tests illustrate many of these checks but are not a production validator. The sample UTC instants have `Z`; callers must validate actual calendar/time values, not only the schema's pattern.

An initial backfill and later incremental request are explicit operations. A cursor or watermark advances only after every accepted page is durably committed; partial or failed pages do not advance it. Retried pages are idempotent by provider, dataset, identity, time and source revision; corrections create a new version with provenance rather than silently overwriting a previous observation. Overlap, retention, conflict resolution, request budgets, closed-session scheduling and source revision semantics require an implementation decision and provider evidence. Restart resumes only from a committed checkpoint; no automatic scheduler is implemented by this proposal.

Source owns provider normalization and explicit unsupported/permission errors; Runtime binds configured Source to Storage; Storage owns immutable local records; Quant derives indicators with formula/version and input basis; Host/UI expose state and user-triggered choices. Observation groups select symbols, not holdings, and a possible TSP projection needs a separately reviewed owner, preview, authorization and conflict behavior. TSP connection details and transport direction remain open. No silent fallback, portfolio overwrite, bidirectional holdings sync or credential exchange is authorized by this proposal. See [#258](https://github.com/yangjingo/WhyJ-Quant/issues/258) and [#264](https://github.com/yangjingo/WhyJ-Quant/issues/264) for the remaining inventory and migration work.
